# GPU substrate research — UIPE vision-svc (post-Fly)

> Generated 2026-06-07 by a 13-agent research workflow (run `wf_2078784e-248`). Replaces the dead Fly GPU substrate.

**Recommendation:** #1: Modal (modal.com) as the self-host substrate. It is the only candidate that maxes out all of UIPE's heavily-weighted criteria at once, and crucially the two that Fly burned you on: (1) NO APPROVAL GATE — verified self-serve, the free Starter tier ships 10 GPU concurrency out of the box, and a 24GB A10/L4 is requested declaratively in the @function decorator with no human in the loop (only a Stripe card on file, a billing requirement, not a waitlist); and (2) VENDOR STABILITY — the strongest signal in the field by a wide margin: $355M Series C (May 2026) at $4.65B, ~$300M ARR, and GPU serverless inference IS the entire product, so deprecating GPUs would mean deprecating the company. It also wins the economics for a single-tenant intermittent tool: verified true scale-to-zero by DEFAULT (idle=$0 unless you explicitly set min_containers>0), 24GB A10 ($1.10/hr) and L4 ($0.80/hr) self-serve, GPU memory snapshots that cut cold starts ~10x, and a recurring $30/mo free credit that almost certainly zeroes your actual bill at this volume. Best Python/FastAPI DX of the self-host options for BOTH the ephemeral eval now and the persistent Phase-4 endpoint, and the strategically coherent home for the later optical-flow CUDA work — one substrate for both tracks. The single watch-item is cold-start latency on each burst (the cost/latency lever): accept cold starts (cheap) rather than keep-warm (~$800/mo always-on) for this profile, and benchmark the real 7B cold-start before committing Phase 4.

**Runner-up:** RunPod — Serverless (Flex workers). Verified true scale-to-zero (per-second, idle GPU=$0; only ~$1-2/mo residual to keep the 15GB model on a network volume so cold starts don't re-download it), self-serve with no approval gate (inferred from the documented account+funds→deploy console flow — medium-high confidence, nothing contradicts it), and strong GPU-is-the-whole-company stability ($120M ARR Jan 2026, 500k+ devs, 31 regions). 24GB-class L4/A5000/3090 at ~$0.68/hr serverless. It loses to Modal on three concrete points: cold-start seconds ARE billed (Modal's snapshots are better and Modal doesn't bill the keep-warm-free path the same way), there's no $30/mo free credit, and serverless requires a handler/load-balancer wrapper rather than a near-verbatim FastAPI drop-in. It's seed-stage ($22M raised, no Series B) vs Modal's $355M Series C — a real but secondary stability gap. Strategic upside that nearly ties it with Modal: the SAME RunPod account gives you raw CUDA Pods, so the later optical-flow work lives on one vendor too. If Modal's per-second rate or decorator lock-in is a concern, RunPod is the drop-in alternative. (Honorable mention as the stability-maximizing single-vendor consolidation bet if UIPE ever wants a hyperscaler: Google Cloud Run GPU — true scale-to-zero, SLA-backed, actively expanding — but its new-account L4-quota friction keeps it at #3.)

**Self-host vs hosted API:** Do BOTH, phased — and let the optical-flow roadmap break the tie, not cost. For the analyze track in ISOLATION, a hosted VLM API wins decisively on cost and ops: at UIPE's intermittent single-tenant volume (a few hundred screenshots/day) Qwen2.5-VL-7B on Hyperbolic (~$0.20/M tokens, verified) or DeepInfra runs ~$1-10/mo with literally $0 idle, zero cold starts, and zero GPU ops. Self-hosting the same workload on Modal/RunPod lands in the same single-digit-to-low-tens $/mo range but adds container, cold-start, and VRAM-fit work for no cost advantage. So if analyze were the ONLY GPU need, hosted API would be the answer, full stop.\n\nBut it isn't. The UIPE roadmap explicitly needs its own CUDA GPU later for the optical-flow track, which a token API fundamentally cannot serve. That makes standing up a self-host substrate non-optional eventually — so doing it for analyze is not wasted, it's a head start on the deploy muscle and a single substrate for both tracks. Net call: (1) RIGHT NOW, unblock the Phase-2 benchmark/eval on a hosted API — Hyperbolic/DeepInfra for the real 7B, or OpenRouter's free 7B endpoint for throwaway A/B runs and provider-failover insurance. This is instant, idle=$0, and lets you validate Qwen2.5-VL on real UI screenshots without any GPU ceremony. (2) STAND UP MODAL when either condition hits: you need your own /v1/analyze contract / detection-shaped output that a token API won't give you, OR the optical-flow CUDA port begins — at which point both tracks share one stable, no-approval-gate, scale-to-zero substrate. Two important caveats: hosted APIs give you no control over weights/quant/version (eval drift — your benchmark may not match a future self-hosted build, so re-validate at the cutover), and they send screenshots off your boundary (a governance consideration self-host avoids). Also note the named-model trap: Together (dedicated-only) and Fireworks (7B not serverless) do NOT offer scale-to-zero hosted 7B — use Hyperbolic/DeepInfra/OpenRouter for the actual 7B.

**Key risks:** 1) COLD STARTS are the universal hidden cost of scale-to-zero self-host. Loading ~15GB into VRAM on each wake is billed at the per-second GPU rate, so real $/request > steady-state. Modal's GPU memory snapshots mitigate best (but were ALPHA in the sources — benchmark the actual 7B cold start before committing Phase 4). RunPod and Cloud Run BILL cold-start seconds; Cloud Run adds a 1-min minimum that punishes chatty bursts (batch eval calls). The keep-warm fix (min_containers>0 / active worker / min-replicas=1) flips any of these to ~$600-800/mo always-on — do NOT use it for this profile. 2) 24GB VRAM HEADROOM is tight. Qwen2.5-VL-7B bf16 is ~15-16GB weights; KV cache + high-res/multi-image vision tokens can OOM a 24GB A10/L4 on long contexts. Plan to quantize (AWQ/INT8/FP8) or cap image resolution, and actually bench VRAM before locking the endpoint to a 24GB card (step-up: A100-40GB or L4→RTX PRO 6000 96GB on Cloud Run). Your MEMORY.md qwen3-vl OOM was CPU/Ollama on the Intel Mac — not relevant to a CUDA card, but a flag to verify empirically. 3) NO-APPROVAL-GATE confidence is uneven. Modal verified high; RunPod inferred (medium-high, no contradicting source — confirm at signup); Cloud Run policy is self-serve but Feb-2026 forum reports show new/trial-graduated accounts hitting default-0 L4 quota needing a (fast, self-serve) request — verify YOUR project's quota first. Azure and Fal custom-serverless have REAL approval gates (avoid for this reason). 4) VENDOR-STABILITY tiers: Modal/Baseten (Series C/E, NVIDIA-backed) and the hyperscalers are safest; RunPod/Cloud Run strong; Cerebrium MEDIUM (single $8.5M seed — startup-mortality, not GPU-exit, risk); Hyperbolic/Novita/Vast WEAKEST (thin/opaque funding or marketplace model) — do not single-source Phase 4 on them right after a rug-pull. 5) NAMED-MODEL SERVING-MODE drift: Together serves Qwen2.5-VL dedicated-only and Fireworks dropped serverless for the 7B — even stable vendors quietly change which mode a model size gets, so don't hard-couple to one provider's serverless availability; route hosted via OpenRouter for failover. 6) Cost estimates throughout are arithmetic on verified per-second/per-token RATES; the per-request seconds and monthly volumes are estimates — benchmark real analyze latency, since monthly $ scales linearly with it. 7) DX lock-in differs: Modal/RunPod take FastAPI close to verbatim; Baseten (Truss predict()) and Replicate (Cog predict.py) require rewriting /v1/analyze — factor the porting cost.
